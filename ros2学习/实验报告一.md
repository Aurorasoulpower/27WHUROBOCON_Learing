实验环境：ROS2 Humble，Ubuntu 22.04，Python 3.10

## 一、实验目的

用 Python 编写 ROS2 发布者与订阅者，实现节点间话题通信；理解定时器间隔（发布频率）、队列长度与 QoS 对通信行为的影响。

## 二、实验原理

话题通信是松耦合的：发布者只往话题发消息、不关心有没有人收；订阅者声明对某话题感兴趣后，系统自动回调处理新消息，双方互不知道对方是否存在。发布频率 = 1 ÷ 定时器间隔；队列长度是待处理消息的缓存上限；QoS 决定消息是否保证送达——`RELIABLE` 不丢但可能积压，`BEST_EFFORT` 满了就丢但更实时。发布端与订阅端 QoS 不兼容时无法建立通信。

## 三、代码说明

### 1. 发布者 student_publisher.py

```python
# TODO 1：创建 Publisher
qos = QoSProfile(
    reliability=ReliabilityPolicy.RELIABLE,
    history=HistoryPolicy.KEEP_LAST,
    depth=10
)
self.publisher = self.create_publisher(String, '/lab1/student_msg', qos)

# TODO 2：创建定时器
self.timer = self.create_timer(0.5, self.timer_callback)

# TODO 3：填写学号
self.student_id = '2025302201006'

# TODO 4：构造并发布消息
def timer_callback(self):
    msg = String()
    msg.data = f"学号: {self.student_id}, 计数: {self.count}"
    self.publisher.publish(msg)
    if self.count % 100 == 0:
        self.get_logger().info(f'发布: {msg.data}')
    self.count += 1
```

`create_publisher` 创建发布者（话题 `/lab1/student_msg`，可靠 QoS、保留最近 10 条）；`create_timer` 每 0.5 秒触发一次回调；回调里构造 `String` 消息写入学号和计数后发布，每 100 条打印一次以免刷屏。

### 2. 订阅者 student_subscriber.py

```python
# TODO 1：创建 Subscriber
qos = QoSProfile(
    reliability=ReliabilityPolicy.RELIABLE,
    history=HistoryPolicy.KEEP_LAST,
    depth=10
)
self.subscription = self.create_subscription(
    String, '/lab1/student_msg', self.message_callback, qos
)

# TODO 2：处理收到的消息
def message_callback(self, msg):
    self.received_count += 1
    if self.received_count % 10 == 0:
        self.get_logger().info(f'收到: {msg.data} | 累计: {self.received_count}')
```

`create_subscription` 订阅同一话题，QoS 与发布者一致以保证兼容；回调里计数并每 10 条打印消息内容与累计条数。

## 五、问题与解决

1. **日志刷屏、统计难观察**：发布与订阅各自每 10 条打印一次，输出太快看不清。改为发布端每 100 条、订阅端每 10 条打印后，统计信息清晰可见。
2. **QoS 不兼容收不到消息**（拓展一）：发布端与订阅端 QoS 不一致时出现 `incompatible QoS` 警告且无消息。把两边同时改成 `RELIABLE`（或同时 `BEST_EFFORT`）后恢复正常。
3. **多订阅者节点名冲突**（拓展二）：同时启动多个同名订阅者会互相顶替。用 `--ros-args -r __node:=subscriber_A/B/C` 重映射节点名解决。

## 六、思考与改进

### 拓展任务完成情况

#### 拓展一：50Hz 高频丢包对比

把发布频率改为 50 Hz（周期 0.02 秒），订阅回调里加 `time.sleep(0.1)` 模拟处理不过来（最多 10 条/秒），分别用 `RELIABLE` 和 `BEST_EFFORT` 运行：

| QoS 策略 | 发布端计数 | 订阅端计数 | topic hz | 现象 | 原因 | 结论 |
|---|---:|---:|---:|---|---|---|
| RELIABLE | 2300 | 400 | ~50.1 Hz | 积压严重，关闭时出现 rclpy 异常 | 可靠传输不丢，队列积压并重传 | 可靠优先，但可能阻塞 |
| BEST_EFFORT | 4800 | 800 | 50.0 Hz | 运行平滑，但丢大量消息 | 队列满后直接丢弃新消息 | 实时优先，允许丢包 |

> 两组运行时长不同，计数为截图时刻值，仅作定性对比。

结论：**“可靠”不等于“快”**。高频传感器数据、处理能力有限时用 `BEST_EFFORT` 可避免卡死；关键指令必须用 `RELIABLE` 保证送达。

【图片占位：50Hz RELIABLE / BEST_EFFORT 对比终端截图】

#### 拓展二：多订阅者协作

一个发布者 + 三个重映射订阅者：

```bash
ros2 run lab1_topics student_subscriber --ros-args -r __node:=subscriber_A
ros2 run lab1_topics student_subscriber --ros-args -r __node:=subscriber_B
ros2 run lab1_topics student_subscriber --ros-args -r __node:=subscriber_C
```

三个订阅者同步收到同一份数据、计数一致。现象：一份数据被多个订阅者同时接收；原因：话题是广播机制，DDS 复制分发给所有已连接订阅者；结论：话题天然支持一对多，适合数据分发与状态广播。

#### 拓展三：launch 一键启动

```python
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        Node(package='lab1_topics', executable='student_publisher',
             name='student_publisher', output='screen'),
        Node(package='lab1_topics', executable='student_subscriber',
             name='student_subscriber', output='screen'),
    ])
```

`ros2 launch lab1_topics lab1.launch.py` 一条命令同时启动两个节点，无需手动开多个终端。launch 文件描述节点启动蓝图，是多节点系统的工程化启动方式。

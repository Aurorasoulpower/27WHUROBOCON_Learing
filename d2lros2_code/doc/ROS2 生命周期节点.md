# ROS2 生命周期节点

## 一、为什么需要生命周期节点

### 1.1 ROS1 的问题

ROS1 里，节点启动顺序无法控制。所有节点一启动就进入工作状态，谁先谁后完全随机。

这在机器人系统里很危险。举几个教材里的例子：

- 传感器还没启动，控制节点已经开始读数据了
- 控制器还没准备好，执行器已经开始接收指令了
- 导航还没初始化，路径规划已经在跑了

结果是：系统时好时坏，报错随机出现，排查起来非常痛苦。

### 1.2 ROS2 的解法

ROS2 提出生命周期节点（Lifecycle Node）的概念：**节点的状态可以被显式控制**。

节点不再“一启动就工作”，而是要经过几个明确的状态阶段，由外部按顺序触发。这样整个系统的启动顺序就变成可控、可检测的了。

## 二、生命周期节点的四个主要状态

生命周期节点是一个状态机。它只有四个主要状态，节点在任何时刻都处于其中之一。

### 2.1 未配置状态（Unconfigured）

节点刚创建时的第一个状态。

- 没有执行任何业务逻辑
- 没有分配资源
- 只处于“已加载”状态

它的主要作用是**错误恢复**。如果节点在后续状态中出错，可以退回到这个状态，重新配置、重新启动。

可以理解为：节点刚出厂，还没配置。

### 2.2 非活跃状态（Inactive）

节点已经完成配置，但不工作。

- 资源已经持有：发布者、订阅者、服务端、客户端都创建好了
- 配置已经就绪：参数已读取、内部变量已初始化
- 但什么都不做：不发布、不接收、不处理

有个细节：传入的数据可以保存在缓冲区中，但不能读取。这样等进入活跃状态后，可以先处理积压的数据。

它的主要作用是**允许重新配置**。比如你想改参数，可以先从活跃退到非活跃，改完再回到活跃，不用重启节点。

可以理解为：装备齐全，但站在原地待命。

### 2.3 活跃状态（Active）

节点正常工作。

- 发布者发布数据
- 订阅者接收并处理数据
- 服务端响应请求
- 定时器触发回调

这就是普通 ROS2 节点的状态。生命周期节点在活跃状态时，和普通节点没有区别。

可以理解为：正式上岗。

### 2.4 已完成状态（Finalized）

节点已经被销毁。

- 资源已释放
- 不再参与任何通信
- 无法再从该状态退出

进入这个状态后，节点就结束了。

可以理解为：退役。

## 三、状态之间的转换

四个状态之间不是随便跳的，每一步转换都有明确的名字和触发方式。

### 3.1 转换路径

```
        ┌─────────────┐
        │ Unconfigured│
        └──────┬──────┘
               │ configure
               ↓
        ┌─────────────┐
        │  Inactive   │
        └──────┬──────┘
               │ activate
               ↓
        ┌─────────────┐
        │   Active    │
        └──────┬──────┘
               │ deactivate
               ↓
        ┌─────────────┐
        │  Inactive   │
        └──────┬──────┘
               │ cleanup
               ↓
        ┌─────────────┐
        │ Unconfigured│
        └──────┬──────┘
               │ shutdown
               ↓
        ┌─────────────┐
        │  Finalized  │
        └─────────────┘
```

### 3.2 主要转换

| 转换 | 从 | 到 | 做什么 |
|------|-----|-----|--------|
| `configure` | Unconfigured | Inactive | 分配资源、读取参数、创建通信对象 |
| `activate` | Inactive | Active | 开始工作，启动发布、订阅、定时器 |
| `deactivate` | Active | Inactive | 停止工作，但保留资源 |
| `cleanup` | Inactive | Unconfigured | 释放资源，回到初始状态 |
| `shutdown` | Unconfigured | Finalized | 销毁节点 |
| `activate` 失败 | Inactive | Unconfigured | 出错时退回去重新配置 |
| `deactivate` 失败 | Active | Inactive | 保留资源但停止工作 |

### 3.3 几个不在主路径上的转换

除了主路径，还有几条特殊路径：

- **从 Active 直接 shutdown**：先 deactivate，再 cleanup，再 shutdown
- **从任意状态出现错误**：退回上一个安全状态
- **从 Active 出现错误**：退到 Inactive，而不是 Unconfigured

这些设计的目的都是：出错时尽可能保留已配置好的资源，减少重启成本。

## 四、状态转换靠什么通信

生命周期节点状态转换，不是靠函数调用，而是靠**服务通信**。

每个生命周期节点会自动提供几个服务：

| 服务 | 作用 |
|------|------|
| `<node>/change_state` | 请求状态转换 |
| `<node>/get_state` | 查询当前状态 |
| `<node>/get_available_transitions` | 查询可用的转换 |
| `<node>/get_available_states` | 查询所有可用状态 |

外部通过调用 `change_state` 服务，告诉节点“你现在要转成 Inactive”，节点执行对应的转换，然后返回结果。

因为是通过服务通信，所以：

- 状态转换可以被远程触发
- 转换结果可以被检测
- 状态可以被查询
- 整个启动过程可以被编排成一条服务调用链

这就是“可控、可检测”的实现方式。

## 五、生命周期节点的意义

### 5.1 启动顺序可控

系统启动时，可以按顺序依次激活节点：

1. 先激活传感器节点
2. 等传感器进入 Active
3. 再激活数据处理节点
4. 等数据处理完成配置
5. 最后激活控制节点

每一步都确认成功后再进行下一步。哪个节点卡住，一目了然。

### 5.2 运行时状态可管理

运行中也可以做状态切换：

- 临时停掉某个节点（deactivate）
- 改参数后重新激活
- 出错了退回重新配置
- 不用重启整个系统

### 5.3 错误恢复有路径

出错时不是直接崩溃，而是退回上一个状态。这样可以：

- 保留已经配置好的资源
- 只重做出错的那一步
- 不丢失整体进度

### 5.4 系统状态可观测

外部可以随时查 `get_state` 服务，知道每个节点当前处于什么状态。整个系统的健康状态是可查询的。

## 六、和普通节点的关系

| 维度 | 普通节点 | 生命周期节点 |
|------|----------|-------------|
| 启动 | 一启动就工作 | 经过状态机逐步进入工作 |
| 状态 | 无显式状态 | 四状态明确 |
| 控制 | 无法从外部控制 | 通过服务控制 |
| 资源管理 | 启动即分配 | 分阶段分配/释放 |
| 错误恢复 | 通常崩溃重启 | 可退回上一个状态 |
| 复杂度 | 低 | 高 |

生命周期节点不是替代普通节点，而是在需要**启动顺序控制、运行时状态管理、错误恢复**的场景下使用。普通的独立功能节点，用普通节点就够了。

## 七、一句话总结

生命周期节点把节点的生命周期拆成四个状态：未配置、非活跃、活跃、已完成。状态之间的转换通过服务触发，可以远程控制、可以查询、可以报错退回。它的价值是让整个机器人系统的启动、运行、恢复变得可控、可检测、可管理。

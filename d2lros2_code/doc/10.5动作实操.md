
# Action 通信实操过程记录

## 一、起点：学概念 + 玩 CLI

先用小乌龟把 Action 的 CLI 工具跑了一遍。

启动 `turtlesim_node` 和 `turtle_teleop_key`，发现同一个键盘控制节点，方向键走话题，G/B/V/C/D/E/R/T 走 Action。按 F 能取消旋转。

然后用 CLI 验证：

```bash
ros2 action list
ros2 action list -t
ros2 action info /turtle1/rotate_absolute
ros2 interface show turtlesim/action/RotateAbsolute
ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.6}"
ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.5}" --feedback
```

不带 `--feedback` 只能看到 Goal 和 Result。带 `--feedback` 能看到执行过程中一连串 `remaining` 在变小。这时直观感受到：Action 比服务多了“过程反馈”。

## 二、建接口包，踩了“找不到生成文件”的坑

创建 `robot_control_interfaces` 接口包，定义 `MoveRobot.action`。配置 `package.xml` 和 `CMakeLists.txt`，编译。

编译完成后去找生成的文件，在 `src/` 下翻，找不到。

排查过程：

- 先用 `find` 在 `install/` 下搜：

```bash
find install/robot_control_interfaces -name "*move_robot*"
```

- 输出一大堆文件，Python 和 C++ 的都有

结论：生成的文件一直在，只是我找错了地方。它们都在 `install/` 下：

- Python 模块：`install/.../local/lib/python3.10/dist-packages/robot_control_interfaces/action/_move_robot.py`
- C++ 头文件：`install/.../include/robot_control_interfaces/robot_control_interfaces/action/move_robot.hpp`

**记住的教训**：ROS2 的生成产物都在 `install/`，不在 `src/`。接口包路径用 `local/lib/python3.10/dist-packages`，普通 Python 功能包用 `lib/python3.10/site-packages`。

## 四、写客户端，再次查错

客户端骨架也是教材给的，我照着自己的理解填。查错时发现：

```python
if not goal_handle.accepted():
```

`accepted` 是属性不是方法，加了括号会报 `TypeError: 'bool' object is not callable`。去掉括号。

编译运行，服务端和客户端跑通了：

- 客户端发目标，服务端接受
- 服务端一边移动一边发反馈
- 客户端收到多次反馈
- 到目标后，客户端收到最终结果

基本的 Action 通信闭环通了。

## 五、做取消功能，卡了好几轮

这是整个 Action 部分最花时间的地方，前后排查了三四轮才成功。

### 5.1 第一轮：服务端没加 cancel_callback

客户端加了取消定时器，定时 5 秒后发取消请求。

跑起来，客户端日志：

```
请求取消目标
```

服务端日志：

```
执行移动机器人
移动了：...
移动了：...
（一直在移动，从头到尾没打印"收到取消请求"）
```

排查：Python 的 `ActionServer` 默认 `cancel_callback` 返回 `CancelResponse.REJECT`，而且不打印任何东西。不覆盖的话，取消被静默拒绝。

改服务端，加三处：

- 导入 `CancelResponse`
- 创建 `ActionServer` 时传入 `cancel_callback=self.cancel_callback`
- 写 `cancel_callback`，返回 `CancelResponse.ACCEPT`

### 5.2 第二轮：取消定时器比目标接受早触发

改完服务端，重跑。

客户端日志出现关键信息：

```
[1791204420.664] 还没有目标，无法取消
[1791204420.665] 目标被接受：）
```

取消比目标接受早了 0.0017 秒。此时 `_goal_handle` 还是 `None`，取消请求根本没发出去。

原因分析：两个定时器都在 `__init__` 里创建：

```python
self.cancel_timer_ = self.create_timer(5, self.cancel_goal)
self.send_goal_timer_ = self.create_timer(1, self.send_goal)
```

`send_goal` 里有一句 `self.action_client_.wait_for_server()`，会阻塞执行器。如果服务端上线花了很久，`send_goal` 一直卡着，执行器不能处理其他回调。`cancel_timer_` 到期后排队等待，等 `send_goal` 一让出执行器，`cancel_goal` 立刻被触发，此时 `goal_response_callback` 还没执行。

改法：把取消定时器的创建移到 `goal_response_callback` 里，等目标被接受后再启动：

```python
def goal_response_callback(self, future):
    goal_handle = future.result()
    if not goal_handle.accepted:
        return
    self._goal_handle = goal_handle
    self._cancel_timer = self.create_timer(3, self.cancel_goal)
    ...
```

### 5.3 第三轮：客户端发出去了，服务端还是没反应

改完定时器时序，重跑。

客户端日志：

```
[1791204517.15] 请求取消目标
```

服务端：

```
（一直在移动，从头到尾没打印"收到取消请求"）
```

客户端确实发出去了，服务端确实没处理。

排查到这里，意识到一个关键问题：服务端用的是 `rclpy.spin(node)`，也就是单线程执行器。

服务端的 `execute_callback` 里有一个 while 循环，要跑好几秒，期间一直占着执行器唯一的线程。取消请求确实通过网络到达了服务端，进入回调队列，但没有线程去处理它。取消回调排着队，等 `execute_callback` 结束才有机会执行。可 `execute_callback` 要等机器人走到 5.0 才结束，那时候取消早就没意义了。

**这就是教材里提过的“rate 死锁”同一类问题。** 教材把多线程执行器注释掉了，改用 `rclpy.spin`，简化了示例。但对取消流程来说，这个简化会导致功能失效。

改法：服务端 main 函数换成多线程执行器：

```python
from rclpy.executors import MultiThreadedExecutor

def main(args=None):
    rclpy.init(args=args)
    node = ActionRobot02("action_robot_02")
    executor = MultiThreadedExecutor()
    executor.add_node(node)
    executor.spin()
    rclpy.shutdown()
```

### 5.4 第四轮：成功

改完服务端执行器，重跑。

服务端日志：

```
[1791204682.904] 收到取消请求，接受
移动了：0.215233605，当前位置：3.06289755
[1791204682.916] 目标取消
```

之后不再有新的“移动了”，机器人停在取消点。

客户端日志：

```
[1791204682.900] 请求取消目标
[1791204682.918] 目标被取消，当前位置 3.0628974437713623
```

服务端和客户端时间几乎同步，位置一致。取消功能完整跑通。

## 六、这轮踩坑的总结

取消功能之所以卡了好几轮，是因为**两个问题叠加**：

- 客户端的取消定时器在目标被接受前触发，`_goal_handle` 是 `None`，取消请求没发出去
- 服务端用单线程执行器，`execute_callback` 的循环占满线程，取消回调排队等不到执行

单独解决任何一个都不够。两个都修了，才通。

## 七、验证清单

整轮实操下来，Action 通信的这些能力都验证过了：

| 能力           | 验证方式                          | 结果 |

## 八、对 Action 的直观感受

跑完整个流程后，对 Action 的定位理解更清晰了：

- Action 把“发目标、收反馈、收结果、发取消”这四件事打包在一起，比服务复杂，但解决了服务覆盖不了的长任务场景
- 反馈是 Action 最有用的部分。没有反馈，客户端只能黑盒等待；有了反馈，客户端随时知道任务执行到哪
- 取消功能必须配合多线程执行器。这是 Action 服务端的一个工程要点，教材简化示例时没强调，但实际项目里绕不过去
- Python 版比 C++ 版简单很多，默认回调帮了大忙，只有需要拒绝目标或允许取消时才需要覆盖默认行为

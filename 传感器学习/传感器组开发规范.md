# 传感器组开发规范

> 适用范围：WHUROBOCON 控制方向传感器组成员。
> 赛季：2027RC。
> 性质：根据组织现有规范整理的个人查阅版，执行时以组长发布的最新通知为准。
> 整理日期：2026-10-24。

## 1. 先记住这些规则

1. 日常调试代码放在组织下的独立项目仓库；测试成功的完整代码再进入 `02-CONTROL/main` 的对应赛季目录。
2. 新目录用短横线，文件名用下划线；Markdown 文档标题和中文字符可以出现在文件名中。
3. 新文件先检查含义，不能出现空格、`final`、`new`、`测试1`、`~$`、`.bak`、`.cache`。
4. 一个提交只做一件事，格式为 `<type>(<scope>): <subject>`。
5. 一个外设或功能对应一对 `.c/.h`；能 `static` 就不全局，能接口访问就不暴露变量。
6. 速度、坐标轴、单位、时间戳、标定参数和硬件版本必须写清楚，避免以后靠猜。
7. 定版文件不覆盖；修改后递增版本号，例如 `v1.0 -> v1.1`。
8. 每个项目目录都必须有 `README.md`，负责人变更时同步更新。

## 2. 代码放在哪里

控制组主仓库是 `02-CONTROL`。

```text
02-CONTROL/
├── README.md              # 控制组介绍、环境、项目 README 模板
├── docs/                  # FAQ、协议、代码规范、器件和调试笔记
├── shared/                # 通用驱动、算法、外设和公共代码，由组长审核
├── 2027RC/                # 当前赛季
│   ├── README.md          # 赛季目标、负责人
│   └── <项目名>/          # 例如 imu-fusion/、camera-pose/
│       └── README.md
└── 2026RC/                # 已归档赛季，只读
```

### 2.1 日常调试

未定型的传感器驱动、标定脚本和联调程序，在组织下建立独立项目仓库维护，自己或与队友共同开发。不要把一套实验代码复制成多个“版本”目录。

### 2.2 定版上传

代码测试成功、接口和文档齐全后，再提交到 `02-CONTROL/main` 的对应赛季目录：

```text
2027RC/<项目名>/
```

不要在调试尚未完成时，把大量临时脚本直接塞入主仓库。传感器板卡和工程的定版文件也按同样原则处理。

### 2.3 公共代码

能被多个项目复用的传感器驱动、通信协议和算法放 `shared/`。公共代码影响范围较大，提交前应经过组长审核，并说明接口变化和兼容性。

## 3. 首次配置

### 3.1 加入组织并配置 SSH

将 GitHub 用户名告诉组长，接受组织邀请后配置 SSH：

```bash
ssh-keygen -t ed25519 -C "你的邮箱@example.com"
cat ~/.ssh/id_ed25519.pub
```

把公钥粘贴到 GitHub 的 **Settings → SSH and GPG keys → New SSH key**。

### 3.2 稀疏检出主仓库

只维护自己负责的目录时，不必下载整个主仓库：

```bash
git clone --filter=blob:none --sparse \
  git@github.com:WHUROBOCON/02-CONTROL.git

cd 02-CONTROL
git sparse-checkout set 2027RC/<项目名> docs shared
```

以后需要查看其他模块时：

```bash
git sparse-checkout add <路径>
```

### 3.3 配置提交身份

```bash
git config --global user.name "姓名首字母缩写"
git config --global user.email "你的邮箱"

git config --global user.name
git config --global user.email
```

如果姓名缩写配置不正确，重新执行设置命令覆盖。提交信息中的作者应与本人一致，便于追溯。

## 4. 仓库命名

### 4.1 主仓库和新建仓库

- 控制组主仓库：`02-CONTROL`。
- 新建仓库前先询问队长或组长，确认不会重复建库。
- 新建个人项目仓库优先采用组织规范的小写短横线形式，例如 `sensor-2027rc-imu-fusion`。
- 如果项目必须归属某个机器人系列，可沿用现有 `27RC_<队别>_<用途>` 风格，但创建前要与组长确认。仓库名是长期引用目标，创建后再改名会影响队友。

仓库名以清楚表达“赛季、归属、用途”为准，避免在一批仓库中混用多种拼写。

### 4.2 现有仓库名参考

组织内已经出现以下名称：

```text
27RC_BR_Chassisclimber
27RC_BR_Chassis
WHU_STM32H7_Template
27_BR_GROUNDCLAW
27RC_BR_Master
27RC_BR_babuJaw
27_RC_TR_Downstairs
27RC_BR_SkyClaw
```

`27RC_BR_*` 是较常见的系列写法，同时也能看到 `27_BR_*`、`27_RC_TR_*` 和大写项目名。它们是现有名称样例。自己建立新仓库时可以作参考。

新仓库命名时遵守以下约束：

- 不擅自修改已有仓库的引用；
- 不在未确认 `BR`、`TR` 含义的项目中使用这些代号；
- 不自行增加第三种“看起来相似”的前缀；
- 把最终仓库名和用途写进项目 `README.md`。

## 5. 文件和目录命名

### 5.1 总原则

命名应当可读、统一、可排序、便于追溯：

- 看到名称能判断内容和所属模块；
- 同一类对象始终使用同一种大小写与分隔符；
- 代码和工程文件名以英文为主；
- Markdown 文档可以使用中文；
- 定版文件带版本号；
- 不依赖 `final`、`latest`、`new` 等无法排序的词。

### 5.2 分隔符

| 对象        | 分隔符                      | 示例                                 |
| ----------- | --------------------------- | ------------------------------------ |
| 目录        | 短横线 `-`                | `imu-fusion/`                      |
| 文件        | 下划线 `_`                | `imu_driver.c`                     |
| Python 脚本 | 下划线 `_`                | `camera_calibrate.py`              |
| 分支        | 斜杠 `/` 分层，短横线分词 | `feature/2027RC/sensor/imu-driver` |
| 版本号      | `v` + 数字                | `v1.0`                             |

历史目录保持原名。新目录和新文件不要继续引入新的分隔规则。

### 5.3 赛季和项目目录

```text
2027RC/
└── imu-fusion/
    ├── README.md
    ├── board/
    ├── inc/
    ├── src/
    ├── test/
    ├── config/
    └── docs/
```

- 赛季目录统一写成 `2027RC/`。
- 项目目录使用全小写英文和短横线，如 `imu-fusion/`、`camera-pose/`、`lidar-comm/`。
- 项目目录不带版本号；版本通过文件名或 Tag 表示。
- 赛季结束后保留原目录并归档，不重命名。

### 5.4 文件命名

通用格式：

```text
[前缀]_[名称]_[版本].[扩展名]
```

前缀用于排序或分类，可以省略：

```text
imu_driver.c
imu_driver.h
imu_test.py
imu_firmware_v1.0.hex
camera_calibration_v1.1.xlsx
```

传感器板相关定版文件可以使用：

```text
schematics_v1.0.pdf
bom_v1.0.xlsx
gerber_v1.0.zip
3d_pcb_v1.0.step
sensor_board_v1.0.epro2
sensor_board_photo_v1.0.png
```

规则：

- 文件名全部小写，单词用下划线；
- 代码、工程和交换文件不使用中文文件名；
- 定版文件必须带 `v主.次` 或 `v主.次.修订`；
- 扩展名保持小写；
- `v1.0` 发布后不直接覆盖，修改时另存为 `v1.1`。

### 5.5 Markdown 文档

不受日期影响的原理和方案文档使用清晰主题名，例如：

```text
传感器组开发规范.md
IMU时间同步.md
相机标定原理.md
```

具体实验使用日期前缀：

```text
2026-10-24_IMU零偏测试.md
2026-10-25_相机重投影误差复测.md
```

同一主题的图片、日志和导出数据处理为：

```text
assets/<主题>/
```

不要把大段二进制数据、原始 rosbag 或大型标定数据集直接复制进学习文档目录。

### 5.6 禁止项

```text
power module v1.c         # 有空格
IMU驱动.c                 # 代码文件使用中文
imu_final.c               # 无法定义“最终”
imu_final2.c              # 应使用 v1.1
imu_new.c                 # 应表达实际版本和用途
~$imu_driver.c            # Office 临时文件
imu_driver.c.bak          # 备份文件
imu.cache                 # 缓存文件
```

## 6. 分支、Tag 和 PR

### 6.1 分支命名

格式：

```text
<类型>/<赛季>/<组别>/<简述>
```

个人临时分支至少保留类型和简述：

```text
<类型>/<简述>
```

传感器项目示例：

```text
feature/2027RC/sensor/imu-driver
fix/2027RC/sensor/camera-timestamp
docs/2027RC/sensor/calibration-guide
fix/lidar-uart-framing
```

约定：

- 使用 `feature/`、`fix/`、`docs/` 等类型前缀；
- 全部小写，用 `/` 分层，用 `-` 分词；
- 分支属于个人工作区，合并后删除；
- 不长期保留多个失联的“测试分支”。

### 6.2 Tag

Tag 仅在发布版本、赛季节点或里程碑需要时使用：

```text
v1.0.0
2027RC-v1.0
v1.0-rc1
```

Tag 应打在主分支的发布提交上，发布后不要修改其指向内容。打错且尚未产生依赖时，删除后重新创建。

### 6.3 PR 前检查

提交 PR 前确认：

- 目标分支和目录正确；
- 只包含本次任务相关改动；
- 已删除调试输出、临时文件和无关格式变化；
- 项目 `README.md` 已更新；
- 传感器接口、单位、坐标轴和版本变化已说明；
- 已写清测试方式、结果和已知限制；
- 公共接口变化不会悄悄破坏已有调用方。

## 7. 提交信息

### 7.1 基本格式

```text
<type>(<scope>): <subject>

[body]

[footer]
```

最常见的一行格式：

```text
<type>: <描述>
```

示例：

```text
feat(sensor-imu): 新增IMU零偏温补
fix(sensor-camera): 修复时间戳重复问题
docs(sensor): 补充相机标定复现步骤
refactor(sensor-can): 拆分报文解析模块
chore: 更新构建配置
revert: 回退IMU滤波参数调整
```

### 7.2 类型（type）说明

| type       | 含义                 | 示例                                     |
| ---------- | -------------------- | ---------------------------------------- |
| `feat`     | 新功能 / 新文件      | `feat(电控): 新增底盘速度闭环`           |
| `fix`      | 修复缺陷             | `fix(硬件): 修复电源芯片封装方向错误`    |
| `docs`     | 文档修改             | `docs: 更新机械组指南安装步骤`           |
| `refactor` | 重构，行为不变       | `refactor(电控): 拆分底盘驱动模块`       |
| `chore`    | 杂务（依赖、配置、CI） | `chore: 更新 .gitignore`                 |
| `revert`   | 回退某次提交         | `revert: 回退电机参数调整`               |

其他少见类型（`perf` 性能、`test` 测试、`style` 格式）按需使用，拿不准就省略。

### 7.3 各部分规则

| 部分        | 要求                                                                                |
| ----------- | ----------------------------------------------------------------------------------- |
| `type`    | 必填、全小写，常用 `feat`、`fix`、`docs`、`refactor`、`chore`、`revert` |
| `scope`   | 建议填写，可用 `sensor-imu`、`sensor-camera`、`sensor-lidar`、`sensor-can`  |
| `subject` | 必填，动词开头，不超过 50 字符，不加句号                                            |
| `body`    | 复杂改动时填写，说明原因、方案和验证                                                |
| `footer`  | 需要时写 `BREAKING CHANGE:`、`Refs: #编号`、`Co-authored-by:`                 |

注意 `type` 与冒号之间有一个空格：

```text
feat: 新增IMU数据读取
```

### 7.4 需要正文的情况

出现以下情况时，应补充原因和验证：

- 修复隐蔽的时序、通信或数据错误；
- 改变传感器接口、默认参数或标定含义；
- 改动可能影响其他人的共享代码；
- 需要在两种方案之间记录设计取舍；
- 当前测试不能覆盖全部边界条件。

示例：

```text
fix(sensor-camera): 修复图像与IMU时间戳偏差

原因：采集线程拿到图像后才读取IMU时刻，导致两者相差一帧。
验证：连续采集30分钟，时间戳偏差始终小于2 ms。
已知限制：高负载下仍需复测。
```

不兼容改动必须写清楚：

```text
BREAKING CHANGE: IMU坐标轴定义由x前-y左改为x前-y右，旧的姿态解算代码不再兼容
Refs: #12
```

### 7.5 避免的提交

| 错误                                   | 改进                                     |
| -------------------------------------- | ---------------------------------------- |
| `更新`                               | `fix(sensor-uart): 修复接收缓冲区越界` |
| `add files`                          | `feat(sensor-imu): 新增IMU驱动模块`    |
| `feat:xxx`                           | `feat: xxx`                            |
| 一次提交塞入驱动、标定、文档和构建改动 | 按逻辑拆成多个提交                       |
| 提交信息声称“测试通过”但没有证据     | 写清测试命令、数据和结果                 |

提交前问自己：三个月后只看到这一行，能否知道改了什么、为什么改。

## 9. STM32 HAL C 工程规范

### 9.1 文件与模块

- 每个外设或功能模块独立成对文件；
- `.c` 与 `.h` 同名；
- 一个文件只负责一类清晰的功能；
- 通用代码和项目专用代码分开；
- 不把相机、IMU、通信和状态机全部塞进一个文件。

示例：

```text
imu_driver.c / imu_driver.h
camera_capture.c / camera_capture.h
can_bus.c / can_bus.h
pid_controller.c / pid_controller.h
```

每个头文件必须有保护宏：

```c
#ifndef IMU_DRIVER_H
#define IMU_DRIVER_H

/* 接口声明 */

#endif /* IMU_DRIVER_H */
```

### 9.2 命名

变量使用小写蛇形：

```c
uint16_t sample_rate_hz;
float    pitch_rad;
uint8_t  uart_rx_data;
```

作用域前缀：

```c
static uint8_t s_rx_index;               /* 文件内静态变量 */
uint16_t g_imu_sample_rate_hz;           /* 跨文件全局变量 */

void Imu_ReadRaw(Imu_RawData_t *p_raw);
```

- 指针使用 `p_` 前缀；
- 文件级静态变量使用 `s_` 前缀；
- 必须跨文件共享的变量使用 `g_模块名_` 前缀；
- 同一语义只保留一个词，例如确定使用 `speed`，就不要同时出现 `velocity` 和 `vel`。

函数采用“模块名_动作”：

```c
void Imu_Init(void);
int Imu_ReadSample(Imu_Sample_t *p_sample);
float Camera_GetFps(void);
int Can_SendFrame(const CanFrame_t *p_frame);
void Uart1_RxCallback(uint8_t data);
```

回调写 `_Callback`，中断服务函数写 `_IRQHandler`。

### 9.3 类型、枚举和宏

类型名使用“模块名_名称_t”：

```c
typedef struct {
    float kp;
    float ki;
    float kd;
} Pid_Param_t;

typedef struct {
    float ax_mps2;
    float ay_mps2;
    float az_mps2;
    uint32_t timestamp_us;
} Imu_Accel_t;
```

枚举类型以 `_t` 结尾，成员全大写并带模块前缀：

```c
typedef enum {
    IMU_STATE_IDLE = 0,
    IMU_STATE_RUNNING,
    IMU_STATE_ERROR,
} Imu_State_t;
```

宏和配置常量全大写并带模块前缀：

```c
#define IMU_SAMPLE_RATE_HZ      200
#define IMU_SPI_TIMEOUT_MS      5
#define IMU_MAX_ABS_ACCEL_MPS2  160.0f
```

不要把裸数字直接用于缓冲区大小、超时、量程或比例换算。

### 9.4 作用域和初始化

优先级：

```text
函数参数/返回值 > 文件内 static > 跨文件 g_ 变量
```

只在单个 `.c` 中使用的变量必须加 `static`。确实需要跨文件共享时：

```c
/* imu_driver.c */
uint16_t g_imu_sample_rate_hz = 0;

/* imu_driver.h */
extern uint16_t g_imu_sample_rate_hz;
```

更推荐通过 getter/setter 隔离可变状态：

```c
static uint16_t s_sample_rate_hz = 0;

uint16_t Imu_GetSampleRate(void)
{
    return s_sample_rate_hz;
}

int Imu_SetSampleRate(uint16_t sample_rate_hz)
{
    if ((sample_rate_hz == 0U) || (sample_rate_hz > IMU_SAMPLE_RATE_HZ)) {
        return -1;
    }

    s_sample_rate_hz = sample_rate_hz;
    return 0;
}
```

模块状态应在 `Imu_Init()` 中集中初始化，不要让不同函数“用到哪、初始化到哪”。

### 9.5 结构体和接口

- 结构体用 `typedef`，类型名带 `_t`；
- 成员用 snake_case；
- 按配置、输入、输出、状态分组；
- 单位写进成员名或注释；
- 跨模块数据尽量用结构体封装，避免一长串无单位参数；
- 需要链表或前向引用时使用带标签的结构体。

```c
typedef struct Imu_Sample_s {
    struct Imu_Sample_s *p_next;

    /* 配置 */
    uint16_t sample_rate_hz;

    /* 输出 */
    float ax_mps2;
    float ay_mps2;
    float az_mps2;
    uint32_t timestamp_us;
} Imu_Sample_t;
```

### 9.6 inline 和函数式宏

短小、频繁调用的内部工具函数可使用 `static inline`。不要为了“看起来更快”强行 `inline` 复杂函数。

优先使用 `static inline` 替代函数式宏。必须使用函数式宏时，每个参数都要加括号：

```c
#define IMU_CLAMP(x, lo, hi) \
    (((x) < (lo)) ? (lo) : (((x) > (hi)) ? (hi) : (x)))

#define ARRAY_SIZE(a) (sizeof(a) / sizeof((a)[0]))
```

不要在函数式宏参数中放自增、赋值等有副作用的操作。

### 9.7 注释

每个 `.c/.h` 文件应有文件头：

```c
/**
 * @file    imu_driver.c
 * @brief   IMU数据采集与单位转换
 * @author  xxx
 * @date    2026-10-24
 */
```

对外接口用 Doxygen 注释说明参数、返回值和单位。单位也可以写进变量名：

```c
float pitch_rad;          /* rad */
uint32_t timestamp_us;    /* us */
uint8_t rx_index;         /* 接收缓冲区写指针 */
```

注释重点解释“为什么”，不要重复代码表面行为。例如：

```c
/* 先锁存再读取，避免高低字节在更新时来自不同采样周期 */
Imu_LatchHighByte();
```

注释语言在同一文件内保持统一。被注释掉的代码不要长期保留，提交前删除，或在注释中说明临时保留原因和期限。

### 9.8 const、头文件和魔法数字

不修改的数据加 `const`：

```c
int Can_SendFrame(const CanFrame_t *p_frame);

static const float s_pid_kp = 1.2f;
```

头文件包含顺序固定，先芯片/HAL，再依赖模块，最后本模块：

```c
#include "stm32h7xx_hal.h"
#include "spi_bus.h"
#include "imu_driver.h"
```

硬件寄存器值、量程换算系数、超时、缓冲区大小等必须命名：

```c
/* 不推荐 */
if (rx_count > 128) {
    return -1;
}

/* 推荐 */
if (rx_count > UART_RX_BUF_SIZE) {
    return -1;
}
```

### 9.9 防御性检查

对外接口应校验指针、范围、长度和状态，并返回明确错误码：

```c
int Imu_ReadSample(Imu_Sample_t *p_sample)
{
    if (p_sample == NULL) {
        return -1;
    }

    if (s_state != IMU_STATE_RUNNING) {
        return -2;
    }

    /* 读取并填充数据 */
    return 0;
}
```

驱动错误要能被上层判断，不要静默返回旧数据而不标记健康状态。

### 9.10 反例速查

| 反例                      | 问题               | 正例                                  |
| ------------------------- | ------------------ | ------------------------------------- |
| `int a1; int a2;`       | 名称没有语义       | `int motor_speed;`                  |
| `extern` 到处暴露状态   | 作用域失控         | `static` 或 getter/setter           |
| `void f(int x, int y)`  | 参数含义不明       | `int Imu_SetRange(uint8_t range_g)` |
| `#define MAX 3000`      | 易冲突             | `#define IMU_MAX_RATE_HZ 3000`      |
| `if (duty > 3000)`      | 裸数字             | `if (duty > IMU_MAX_DUTY)`          |
| 一个 `.c` 包办所有逻辑  | 模块边界不清       | 按设备/功能拆分                       |
| 头文件无保护宏            | 可能重复包含       | `#ifndef ...` 保护                  |
| `#define SQUARE(x) x*x` | 优先级和副作用问题 | `static inline` 或完整加括号        |

## 10. 传感器工程的额外要求

### 10.1 统一记录硬件和接口

每个传感器模块至少记录：

- 传感器型号、硬件版本和通信接口；
- I2C 地址、SPI 片选、UART 波特率或网络地址；
- 采样率、量程、分辨率、滤波配置和供电条件；
- 数据单位、正方向、坐标轴和坐标系；
- 时间戳来源、触发方式和同步方案；
- 固件、SDK、驱动和标定文件的版本；
- 已知误差、延迟、失效模式和恢复方式。

硬件或参数变化会影响数据含义，不能只更新代码而不同步 README。

### 10.2 单位、坐标轴和时间

- 距离统一标明 `m` 或 `mm`，角度标明 `rad` 或 `deg`；
- 在变量名、结构体字段或接口注释中写明单位；
- 写清右手/左手坐标、轴方向和传感器安装方向；
- 图像时间戳、IMU 时间戳和系统时间使用同一时钟域标注；
- 存在触发、曝光、传输和处理延迟时，要分别记录；
- 滤波和标定参数变化时，记录对应数据版本。

### 10.3 标定参数

标定文件必须能回答：

- 哪台设备；
- 什么分辨率、量程和采样率；
- 什么温度、对焦状态或安装状态；
- 谁采集、何时采集；
- 用什么工具和命令处理；
- 如何验证、误差有多大；
- 参数是否仍适用于当前硬件。

不要把仅适用于一台设备的参数写成全局默认值。定版参数发生变化时递增版本，并在项目变更记录中说明。

### 10.4 并发、缓冲区和实时性

- 明确驱动由主循环、中断还是 RTOS 任务调用；
- 中断与任务共享数据时使用有界缓冲和明确同步方式；
- 不阻塞中断执行长时间总线访问或打印；
- 为缓冲区写满、丢帧、通信超时和重试设计可观察状态；
- 在 README 或测试中记录正常延迟、抖动和最坏情况。

### 10.5 验证

至少保留以下证据中的适用项：

- 可重复执行的构建、烧录和启动步骤；
- 原始数据、处理结果和可视化截图；
- 采样率、丢帧率、延迟和误差指标；
- 长时间运行和异常恢复结果；
- 标定前后对比；
- 与上层控制或 ROS 2 链路的联调结果；
- 未通过的项目和已知限制。

结论要区分：

```text
已验证 / 待验证 / 未开始 / 阻塞
```

不能用“应该可以”代替测试证据。

## 11. 日常 Git 流程

### 11.1 开始任务

```bash
git switch main
git pull
git switch -c feature/2027RC/sensor/imu-driver
git status
```

也可以直接从当前最新主分支创建：

```bash
git switch -c fix/2027RC/sensor/imu-timeout main
```

### 11.2 提交

先检查改动范围：

```bash
git status
git diff
git diff --staged
```

按逻辑提交：

```bash
git add imu_driver.c imu_driver.h
git commit -m "feat(sensor-imu): 新增IMU采样驱动"

git add README.md
git commit -m "docs(sensor-imu): 补充采样接口说明"
```

带正文：

```bash
git commit -m "fix(sensor-imu): 修复采样时间戳偏移" \
  -m "原因：时间戳记录位置晚于DMA完成回调。验证：连续采集30分钟无重复和倒退。"
```

### 11.3 推送与 PR

```bash
git push -u origin HEAD
```

然后在 GitHub 发起 PR，说明：

- 改了什么；
- 为什么改；
- 如何验证；
- 对接口、参数和队友的影响；
- 尚存风险和后续工作。

### 11.4 修改未推送的提交

只修正自己尚未推送的提交：

```bash
git commit --amend -m "fix(sensor-imu): 修复采样忙等超时"
```

已经推送或他人可能依赖的提交不要直接 `amend`。不要为了掩盖提交历史问题而随意强推。

## 14. 材料之间的差异如何处理

现有文档存在少量历史差异：

- 控制组指南使用 `02-CONTROL`，早期命名材料使用 `02-E_CONTROL`；
- 文件命名要求小写，但部分现有仓库名使用大写、下划线或不同前缀；
- 提交示例中同时出现中文和英文 scope，但都强调 scope 要能准确指向模块。

处理原则：

1. 已有仓库、目录和提交历史不批量改名；
2. 新内容选择当前项目中占主导、且组长确认的写法；
3. 主仓库统一引用 `02-CONTROL`，旧名称作为历史别名保留；
4. 新建仓库前先确认，避免制造第四种相似格式；
5. 规则冲突时，以组织最新正式文档和组长通知为准，并回写项目 README。
